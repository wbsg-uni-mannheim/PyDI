# Difficulty Dimensions for Synthetic Use-Case Generation

This document collects the controllable difficulty dimensions per pipeline stage. Each dimension describes a specific aspect that can be tuned to make a benchmark easier or harder for that stage.

## Evaluation Approach

To avoid a combinatorial explosion of use cases (one per dimension combination), we define a small number of **composite difficulty profiles** (e.g., *easy*, *medium*, *hard*) that set all dimensions together uniformly. A "hard" use case is hard across the board — all dimensions are set to their challenging end. This keeps the number of generated use cases manageable (~2-3 per domain) and makes each profile unambiguous and easy to communicate.

Optionally, to isolate the impact of individual dimensions, we can additionally create **ablation use cases** for the most interesting dimensions: take the *hard* profile and relax exactly one dimension to *medium* and then to *easy*. The performance difference between the full hard profile and each ablation reveals that dimension's marginal contribution to difficulty.

## Cross-Stage Dimension Links

Several difficulty dimensions reflect the same underlying data property affecting multiple pipeline stages. When setting a composite difficulty profile, these linked dimensions move together — they are not independent knobs but different consequences of the same generation choice.

| Shared Data Property | Affected Dimensions (pipeline order) | Relationship |
|---|---|---|
| Surface augmentation intensity | Representation Heterogeneity (Blocking) · Corner-Case Difficulty (Entity Matching) · Conflict Subtlety (Data Fusion) | A single augmentation intensity parameter drives all three stages. Heavy augmentation (stacked abbreviations, typos, reformulations, missing tokens) erodes the signals blockers rely on, creates hard-positive pairs for the matcher, *and* introduces plausible-looking value disagreements for the fusion engine. Mild augmentation preserves blocking signals, produces easy matches, and yields obvious conflicts. |
| Entity similarity structure in domain | Candidate Density (Blocking) · Corner-Case Ratio (Entity Matching) | Generating many inherently similar but distinct entities in the same domain niche (e.g., many smartphones from the same brand, many movies in the same genre and year) creates large blocks with many non-matching pairs *and* pushes more entity pairs near the decision boundary. The generation choice of how many similar entities to place in overlapping domain niches drives both. |
| Attribute coverage per source | Blocking Key Completeness (Blocking) · Record Completeness (Entity Matching) · Source Density (Data Fusion) | A single generation parameter (per-source attribute drop rate) drives all three stages, but with qualitatively different consequences. For blocking, missing key attributes make records entirely *unreachable* — they are placed in no block and cannot be recovered regardless of blocker sophistication. For entity matching, missing attributes gradually degrade comparison signals but the pair is still evaluated. For fusion, sparse attribute coverage limits cross-validation ability. The blocking consequence is binary (reachable or not), while the matching and fusion consequences are gradual. |
| Representations per entity | Entity Group Size Variance (Entity Matching) · Source Density + Conflict Rate (Data Fusion) | Entities that appear in more sources produce more candidate pairs for matching *and* provide more values per attribute for fusion. More representations increase both the opportunity for fusion cross-validation and the likelihood of conflicting values. |
| Normalization residuals | Format Heterogeneity + Unit & Scale Diversity (Normalization) · Representation Heterogeneity (Blocking) | If normalization fails to standardize values, the residual format and unit differences propagate directly into blocking keys and matching features, manifesting as representation heterogeneity that the blocker must absorb. A single generation parameter (how many distinct formats and units are placed across sources) determines both the normalization challenge and the downstream blocking difficulty. |
| Value corruption propagation | Noise & Corruption (Normalization) · Corner-Case Difficulty (Entity Matching) · Conflict Rate (Data Fusion) | Typos, encoding artefacts, and malformed values that survive normalization degrade string similarity scores during entity matching (the same effect as heavy surface augmentation, manifesting as increased corner-case difficulty) and appear as spurious disagreements during data fusion (inflating the conflict rate). The generation choice of how much noise to inject into raw source values controls all three consequences. |
| Value ambiguity propagation | Value Ambiguity (Normalization) · Conflict Rate + Conflict Subtlety (Data Fusion) | Silently misinterpreted values (e.g., a 1000× error from a locale-dependent number format) create artificial conflicts in fusion that look like genuine source disagreements. The generation choice of how many ambiguous representations to use for numeric/date values drives both the normalization challenge and the resulting fusion difficulty. |
| Column naming conventions across sources | Naming Heterogeneity (Schema Matching) · Representation Heterogeneity (Blocking) | Unlike the other links in this table, this is a correlational heuristic rather than a direct causal mechanism: the same style of surface divergence (abbreviations, jargon, opaque codes) applied to column names during schema generation also tends to appear in cell values. When setting naming heterogeneity high in a difficulty profile, value-level representation heterogeneity should be set high as well for consistency, and vice versa. |

## Schema Matching

Schema matching identifies correspondences between source column schemas and a target schema. Its success is measured by precision and recall of discovered column mappings. PyDI provides four complementary matcher strategies — label-based (column name similarity), instance-based (value distribution similarity), duplicate-based (co-occurrence in known record pairs), and LLM-based (semantic reasoning over names and samples) — each relying on different signals.

| Dimension | Description | Examples |
|---|---|---|
| **Naming Heterogeneity** | How much source column names diverge from target column names. At low difficulty, source columns use identical or near-identical names to the target (e.g. `release_date` → `release_date`), and label-based matchers succeed with minimal threshold tuning. At high difficulty, source columns use domain jargon, abbreviations, opaque codes, or entirely unrelated naming conventions (e.g. `yr` for `releaseYear`, `metascore` for `criticScore`, or `col_7` for `revenue`), defeating label-based matching entirely and requiring instance-based or LLM-based fallback. | *Easy:* `release_date` ↔ `releaseDate` — casing/delimiter variation; Jaro-Winkler similarity >0.85. *Hard:* `yr` ↔ `releaseYear`, `metascore` ↔ `criticScore`, `col_7` ↔ `revenue` — no lexical overlap; label-based matcher scores near zero. |
| **Schema Completeness** *(Scenario 2 only)* | How much the source and target schemas overlap in terms of covered attributes. At low difficulty, every target column has a corresponding source column and vice versa (high bidirectional coverage), with few or no unmapped columns on either side. At high difficulty, sources are missing many target attributes (requiring correct null mappings) *and* contain many extra columns with no target correspondence (distractors that could trigger false-positive mappings). The combination of missing target attributes and extra distractor columns is harder than either alone: the matcher must simultaneously avoid mapping distractors to target columns *and* correctly leave target columns unmapped. Not applicable to Scenario 1, where the original schema structure and column set are preserved. | *Easy:* Source has 10 columns, target has 10 columns, 9 have true correspondences — one unmapped column per side. *Hard:* Source has 20 columns, target has 12 columns, only 6 have true correspondences — the matcher must correctly leave 6 target columns unmapped and ignore 14 distractor source columns. |
| **Semantic Ambiguity** *(Scenario 2 only)* | How many source columns could plausibly map to the same target column based on name, type, or value distribution overlap. At low difficulty, each source column has a clearly distinct semantic role — column names, data types, and value distributions unambiguously distinguish candidates. At high difficulty, multiple source columns share similar names, identical data types, and overlapping value ranges, making them near-interchangeable candidates for the same target column. This forces matchers to rely on subtle distributional differences or external context to disambiguate. Not applicable to Scenario 1, where the original column set does not introduce new ambiguous columns. | *Easy:* Source has one date column (`release_date`) and one score column (`rating`) — no ambiguity. *Hard:* Source has `score_1`, `score_2`, `score_3` (all float, 0–100) corresponding to `criticScore`, `userScore`, and `popularityScore` — the matcher must distinguish three semantically similar columns. |

## Normalization

Normalization transforms raw attribute values into standardized forms (consistent units, date formats, codes, scales) so that downstream blocking and matching operate on comparable representations. Its success is measured by what fraction of values are correctly standardized and whether the chosen transformations preserve semantic meaning.

| Dimension | Description | Examples |
|---|---|---|
| **Format Heterogeneity** | How many distinct surface formats represent the same semantic type within and across sources. At low difficulty, each attribute uses a single consistent format across all sources (e.g., all dates are ISO 8601), and the normalizer needs only one parser per column. At high difficulty, the same attribute appears in many formats across sources — and even within a single source column — requiring the normalizer to detect and handle each variant. This dimension covers dates, numbers, phone numbers, country codes, and any other typed attribute. | *Easy:* All dates are `"2024-03-15"` — a single `%Y-%m-%d` parser suffices. *Hard:* Dates appear as `"March 15, 2024"`, `"15/03/2024"`, `"2024-03-15"`, `"03-15-24"`, and `"15. März 2024"` within the same column — the normalizer must detect and handle five distinct formats, including a locale-specific one. |
| **Unit & Scale Diversity** | How many different units and scale modifiers appear for quantity attributes, and whether they span measurement systems or use ambiguous notation. At low difficulty, quantity columns use a single unit or a small set of units within one measurement system (e.g., all metric), and scale modifiers are absent or consistent (e.g., always "MEUR"). At high difficulty, quantities mix measurement systems (metric and imperial), include diverse scale modifiers ("5M", "5 million", "5000k", "5 MEUR"), and some values omit units entirely, forcing the normalizer to infer from context. | *Easy:* Revenue column uses `"MEUR"` throughout — a single scale expansion rule handles everything. *Hard:* Revenue values include `"5.2 MEO"`, `"$5.2 million"`, `"5200 kUSD"`, `"5,200,000"`, and `"5.2M"` — the normalizer must detect and reconcile multiple scale notations, currencies, and bare numbers. |
| **Value Ambiguity** | How many values have multiple plausible interpretations without external context. At low difficulty, values are unambiguous — types and formats are clear from the value alone. At high difficulty, values require context or conventions to interpret correctly: locale-dependent number formats ("1,234" as 1234 in US vs 1.234 in Europe), percentage vs decimal ambiguity (is 0.5 a percentage representation or half?), overloaded abbreviations ("5k" as salary 5000 vs distance), and date ambiguity ("01/02/03" as M/D/Y vs D/M/Y). Incorrect disambiguation silently corrupts values, making this dimension especially impactful on downstream quality. | *Easy:* `"$1,234,567.89"` — currency symbol and consistent US formatting make parsing unambiguous. *Hard:* `"1.234"` in a revenue column from a German source — could be 1234 (German decimal separator) or 1.234 (US notation); the normalizer must infer the locale convention to avoid a 1000× error. |
| **Noise & Corruption** | How many values are malformed, contain typos, encoding artefacts, or are partially corrupted, causing standard parsers to fail. At low difficulty, values are clean — well-formatted with few nulls — and standard parsers succeed on nearly all rows. At high difficulty, values contain OCR-style errors in units ("kilmoeters"), garbled encoding ("München" as "MÃ¼nchen"), truncated strings, embedded HTML entities, and high null rates, requiring robust fallback strategies and graceful degradation. The `on_failure` policy (keep, null, raise) becomes a critical configuration choice. | *Easy:* Country column contains clean names like `"Germany"`, `"France"`, `"United Kingdom"` — pycountry resolves all. *Hard:* Country column contains `"Gemany"`, `"DEUTCHLAND"`, `"DE "` (trailing whitespace), `"Ã–sterreich"` (encoding artefact), and 30% nulls — standard lookup fails on most values without fuzzy matching or encoding repair. |

## Blocking

Blocking reduces the O(n²) comparison space by grouping records so that only within-group pairs reach the entity matcher. Its two competing goals are **pairs completeness** (recall of true matching pairs in the candidate set) and **reduction ratio** (fraction of the full Cartesian product pruned). Both blocking dimensions are closely related to entity matching dimensions — they reflect the same underlying generation choices manifesting at the blocking stage rather than the matching stage. The cross-stage links table above makes these connections explicit.

| Dimension | Description | Examples |
|---|---|---|
| **Representation Heterogeneity** | How much the representations of matching entities diverge across sources, from the perspective of the signals that blockers rely on. This affects all blocker types, though through different mechanisms: key-based blockers (StandardBlocker) lose exact-match overlap, token-based blockers (TokenBlocker) lose shared tokens, sorted-neighbourhood blockers lose sort-key proximity, and embedding-based blockers see reduced cosine similarity. At low difficulty, matching records share most of their surface form across sources (minor casing or whitespace differences), so even simple blocking strategies recover nearly all true pairs. At high difficulty, stacked surface augmentation — abbreviations, token reordering, reformulations, missing tokens — erodes the signals that every blocker type depends on, requiring more aggressive strategies (larger windows, lower similarity thresholds, embedding-based approaches) that in turn inflate the candidate set. Controlled by the same surface augmentation intensity that drives Corner-Case Difficulty for entity matching. | *Easy:* "The Shawshank Redemption" vs "the shawshank redemption" — StandardBlocker on lowercased title recovers the pair; TokenBlocker shares all tokens; EmbeddingBlocker sees cosine similarity >0.95. *Hard:* "The Shawshank Redemption" vs "Shawshank Red. (Darabont '94)" — StandardBlocker on title misses it; TokenBlocker recovers it only via the shared token "Shawshank"; SortedNeighbourhoodBlocker may miss it if sort keys diverge; EmbeddingBlocker sees reduced but likely still viable similarity (~0.6–0.8). |
| **Candidate Density** | How many distinct entities share similar values in the attributes that blockers naturally use as grouping criteria, determining block sizes and the ratio of non-matching to matching pairs in the candidate set. At low difficulty, the entity population is diverse — few entities share the same combination of key attributes (year, genre, brand, category), so blocks are small and most within-block pairs are true matches. At high difficulty, many distinct entities cluster in the same domain niches (e.g., dozens of action movies from 2023, hundreds of Samsung smartphones), creating large blocks dominated by non-matching pairs. This degrades the reduction ratio and forces the blocker to either use finer-grained keys (losing recall) or pass a noisy candidate set to the matcher. Controlled by the same entity generation choices that drive Corner-Case Ratio for entity matching: generating many similar-but-distinct entities in overlapping niches increases both candidate density and the fraction of hard negatives. | *Easy:* Blocking movies on (decade, first\_title\_word): most blocks contain 2–5 entity groups — candidate set is ~5× true pairs. *Hard:* Blocking products on (brand): popular brands like "Samsung" or "Apple" yield blocks with 200+ entity groups — candidate set is ~500× true pairs; the blocker must use finer-grained keys (sacrificing recall) or accept the noise. |
| **Blocking Key Completeness** | Whether records have populated values in the attributes that blockers use for grouping. Unlike Record Completeness for entity matching — where missing attributes gradually reduce comparison signals but the pair is still evaluated — missing blocking key attributes make records entirely *unreachable*: they are placed in no block and produce no candidate pairs, regardless of blocker sophistication. At low difficulty, most records have populated values in natural blocking key attributes (title, name, year) across all sources, so few true pairs are lost to missing keys. At high difficulty, many records are missing the attributes that blockers would use, making them invisible to key-based, token-based, and sorted-neighbourhood blocking. Only embedding-based blockers that can fall back on alternative text columns may partially recover these records. Controlled by the same per-source attribute drop rate that drives Record Completeness for entity matching, but with the distinct binary consequence of block exclusion rather than gradual signal loss. | *Easy:* 95% of records have title and year populated — StandardBlocker on (year, title\_prefix) reaches nearly all true pairs. *Hard:* 40% of records in Source B are missing the title attribute — these records are excluded from any title-based blocking strategy, and the true pairs involving them are irrecoverable unless the blocker uses an alternative attribute (e.g., director + year) or embedding-based fallback over remaining text fields. |

## Entity Matching

Entity matching classifies candidate pairs as matches (same real-world entity) or non-matches. We separate matching corner cases into their *difficulty* (how hard individual corner cases are) and their *ratio* (how many corner cases exist), since the two are controlled through different generation mechanisms: difficulty is tuned via surface augmentation intensity, while ratio requires adding or removing entities. Two additional dimensions capture information availability and entity representation structure.

| Dimension | Description | Examples |
|---|---|---|
| **Corner-Case Difficulty** | How hard the individual corner cases are to classify correctly. This covers both hard positives (true matches with low surface similarity) and hard negatives (true non-matches with high surface similarity). At low difficulty, hard positives differ through a single transformation type (e.g., only minor typos) and hard negatives share a category but differ on key attributes. At high difficulty, hard positives are created by stacking multiple heterogeneity types — typos, abbreviations, synonyms, missing values, and reformulations applied simultaneously. Hard negatives at high difficulty differ in only a single discriminating attribute value while sharing everything else. Hard-positive difficulty is controlled by the intensity and type mix of surface augmentation applied to existing matched pairs. Hard-negative difficulty is controlled by augmenting existing non-matching pairs to be more similar (Scenario 1) or by generating inherently similar but distinct entities (Scenario 2). | *Easy hard positive:* "The Shawshank Redemption (1994)" vs "the shawshank redemption, 1994" — only casing and punctuation differ (single transformation type). *Hard hard positive:* "Shawshank Redemption" vs "Rita Hayworth and Shawshank Redemption · King · '94" — abbreviation + added author + reformatted year + dropped article (multiple stacked types). *Easy hard negative:* "The Matrix (1999, Sci-Fi)" vs "The Matrix Reloaded (2003, Sci-Fi)" — same franchise but clearly different year and title suffix. *Hard hard negative:* "iPhone 14 Pro 128GB Space Black" vs "iPhone 14 Pro Max 128GB Space Black" — differ in a single word. |
| **Corner-Case Ratio** | The fraction of entity pairs in the candidate set that are corner cases — hard positives or hard negatives near the decision boundary. At low difficulty, most matches are obvious (high similarity) and most non-matches are obvious (low similarity), with only a small fraction of pairs being ambiguous. At high difficulty, a large fraction of pairs sit near the decision boundary. In Scenario 1, the ratio of existing corner cases is largely fixed by the original use case data; changing it requires adding entities — injecting new near-duplicate entities increases hard negatives, while adding heavily augmented source variants of existing entities increases hard positives. In Scenario 2, the ratio is directly controllable during entity generation and source splitting. | *Low:* 20% of candidate pairs are corner cases — a simple threshold on string similarity resolves may resolve much of the benchmark. *High:* 80% of candidate pairs are corner cases — no single similarity threshold cleanly separates matches from non-matches, and the matcher must learn nuanced decision boundaries. |
| **Record Completeness** | How many attributes per record are populated and available for comparison. At low difficulty, records are mostly complete across all sources, giving the matcher many independent comparison signals (title, year, director, genre, rating, etc.). At high difficulty, records are sparse — many attributes are null — and different sources populate different attribute subsets, leaving few shared non-null attributes for a given pair. This forces the matcher to make decisions from limited evidence, amplifying the impact of the other dimensions. Controlled during generation via per-source attribute drop rates. | *Easy:* Both records have title, year, director, genre, and rating filled in — five independent comparison signals. *Hard:* Record A has only title and year; Record B has only title and genre — only title can be compared, and it may be ambiguous alone (e.g., multiple films named "Crash"). |
| **Entity Group Size Variance** | How uniform or skewed the number of source representations per entity is. At low difficulty, every entity appears exactly once per source, creating clean pairwise comparisons with predictable structure. At high difficulty, some entities appear in all sources (or even multiple times within a single source as within-source duplicates) while others appear in only one source, creating highly variable group sizes. This complicates both the matching step (the matcher sees a mix of well-represented and under-represented entities) and post-clustering (connected components can grow large for popular entities, while singleton entities produce no true-positive pairs at all). Controlled during generation by varying per-entity source coverage and injecting within-source duplicates. | *Easy:* Every entity appears in exactly 3 out of 3 sources — uniform group size of 3, predictable structure. *Hard:* Popular entities appear in all 4 sources with 2 within-source duplicates (group size 6), while niche entities appear in only 1 source (group size 1) — the matcher and clusterer must handle both extremes. |

## Data Fusion

Conflict resolution in PyDI operates independently per attribute. Within a difficulty profile, all dimensions are set uniformly across attributes to keep the benchmark unambiguous. Per-dimension metric slicing (see Evaluation Approach) can still reveal which dimensions drive performance differences.

| Dimension | Description | Examples |
|---|---|---|
| **Conflict Rate** | For a given attribute, the fraction of record groups (entities) where sources provide disagreeing values. At low difficulty, sources rarely disagree on an attribute across entities — e.g. only 10% of entities have conflicting revenue values. At high difficulty, a large fraction of entities have conflicting values for that attribute — e.g. 75% of entities have sources that disagree on revenue. | *Low:* Only 2 out of 20 entities have conflicting revenue values across sources. *High:* 15 out of 20 entities have conflicting revenue values. |
| **Conflict Subtlety** | For a given attribute, how plausible the incorrect conflicting values are. At low difficulty, conflicts involve obviously wrong values that are simple to filter out. At high difficulty, conflicts are near-misses where multiple values are plausible without external knowledge. | *Easy:* Revenue listed as `$3.5B` vs `$0` — the zero is clearly erroneous. *Hard:* Revenue listed as `$3.5B` vs `$3.7B` — both are plausible and the correct value is ambiguous without a trusted reference. |
| **Source Density** | For a given attribute, how many sources provide a non-null value across entities. At low density, only 1-2 sources ever carry that attribute, so there is nothing to cross-validate against and the fusion engine must accept whatever is available. At high density, most sources provide the attribute, giving voting and comparison strategies more signal. | *Low density:* Only 2 out of 4 sources provide revenue data, limiting cross-validation to a single comparison. *High density:* All 4 sources provide revenue data, enabling majority voting or outlier detection. |
| **Trust Ambiguity** | For a given attribute, whether source reliability is clearly differentiated or indistinguishable. At low difficulty, one source is consistently correct for that attribute, and source-level strategies (e.g., favour a known-reliable source) resolve conflicts easily. At high difficulty, no source is consistently reliable for that attribute, and the fusion engine cannot rely on a single source preference. This dimension is especially impactful when errors are correlated within a source (e.g., a source confuses two entities, causing systematic errors across multiple related attributes), since the fallback of per-attribute voting degrades. | *Easy:* For revenue, Source A is always correct; the strategy simply favours Source A. *Hard:* For revenue, Source A is correct 60% of the time, Source B 55%, and Source C 50% — no clear winner, and per-attribute voting is unreliable. |
