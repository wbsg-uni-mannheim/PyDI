# Committee Finalization — SM / EM / Fusion

**Inserted before S4b in [plan_s1_scale.md](plan_s1_scale.md).** Finalize the algorithm rosters for the three per-use-case committees (schema matching, entity matching, data fusion) *before* running the `companies-small` sanity check. Reason: S4b validates the full pipeline end-to-end including the committees; if the committees are still in flux, any S4b failure requires re-validation after each roster change. Freeze the rosters once, then gate S4b on a stable configuration.

**Methodology in one sentence:** for each committee, (1) inventory what's already covered in [../literature-search-generation/](../../literature-search-generation/), (2) run a targeted external literature search (Google Scholar + VLDB / SIGMOD / EDBT / WWW proceedings + the Mannheim group's recent work), (3) produce a ranked shortlist with selection rationale, (4) freeze the roster in the committee YAML and smoke-test it.

**All three committees are user-directed.** C1 set the precedent: C1.3's scored shortlist was advisory; the final roster decision (add Magneto in C1.5 despite the C1.3 defer) was user-directed. C2 and C3 follow the same pattern — substeps .1/.2/.3 produce evidence, the user picks the roster, substep .4 implements. The scoring rubric in Step (iii) remains the default heuristic but the user can and will override it.

## Scope

- **In scope:** (a) selecting which algorithms belong in each committee, (b) the rationale for inclusion/exclusion recorded alongside each member, (c) a YAML update that is schema-valid against `test_committee_configs.py`, (d) a tiny smoke test per committee that exercises every member on a minimal fixture.
- **Out of scope:** retraining any learned models beyond Ditto (that's S5 / Phase C), running the full knob variant pipeline (that's S4b/S5), extending PyDI's extension-point hierarchy with wholly new abstract classes (would be a separate refactor plan).

## Shared methodology

Applied identically in C1, C2, C3.

### Step (i) — Inventory the existing literature portfolio

Read [../literature-search-generation/INDEX.md](../../literature-search-generation/INDEX.md) + [METHODS_REGISTRY.md](../../literature-search-generation/METHODS_REGISTRY.md). List every paper whose method is directly usable for the committee. Annotate each entry with:
- **method class** (e.g. string-similarity, embedding, PLM, LLM prompt, rule-based, statistical)
- **maturity** (production / research code / paper-only)
- **coverage axis** it would fill in the committee (see per-committee axis tables below)
- **dependency cost** (existing PyDI primitives / needs adapter / needs retraining / external API)

Output: `knobs/committee_review/<committee>_portfolio.md` with a table of known methods.

### Step (ii) — Targeted external literature search

Query set per committee is listed in C1/C2/C3 below. For each query:
- Google Scholar top-20 results, 2022-onwards (last ~4 years = post-Ditto, post-transformer era).
- VLDB / SIGMOD / EDBT / WWW proceedings 2023-2026 for "schema matching" / "entity matching" / "data fusion" tracks.
- ACL / EMNLP / NAACL 2023-2026 for LLM-era variants (especially EM + SM).
- The Mannheim WBSG GitHub org ([github.com/wbsg-uni-mannheim](https://github.com/wbsg-uni-mannheim)) for internally-developed methods we should consider preferring.
- Follow the "cites this paper" graph from the anchors in step (i).

For each candidate *not* already in the portfolio, add a lightweight `literature-search-generation/<slug>/paper.md` card (same frontmatter schema as the existing entries — see [METHODS_REGISTRY.md](../../literature-search-generation/METHODS_REGISTRY.md)) with title, venue, year, method class, code availability, key idea. Full paper cards (implementation-ready level) only for the shortlisted methods; everything else gets a one-line entry.

Output: `knobs/committee_review/<committee>_external.md` — a ranked table of candidates with citations, plus the new `paper.md` cards.

### Step (iii) — Candidate shortlist + scoring rubric

Score each candidate (portfolio ∪ external) on five axes, 0-3 each:

| Axis | 0 | 1 | 2 | 3 |
|---|---|---|---|---|
| **Signal diversity** | redundant with existing member | partial overlap | distinct signal class | distinct + currently absent |
| **SOTA alignment** | outdated | baseline | competitive | SOTA on a recent benchmark |
| **Integration cost** | rewrite PyDI internals | new adapter | existing adapter | drop-in |
| **Determinism / reproducibility** | non-deterministic, no seed | flaky, workarounds | seeded, stable | fully deterministic |
| **Runtime budget fit** | infeasible on MPS/CPU | GPU-required | GPU-preferred | CPU-tractable |

Committee slot cutoff: total score ≥ 10, no axis scoring 0. Total slots per committee: 5-7 members (see per-committee sections for the exact axis targets).

Output: `knobs/committee_review/<committee>_shortlist.md` — scored table with the proposed roster highlighted and one-paragraph rationale per included *and* excluded candidate (exclusion rationale prevents relitigation).

### Step (iv) — Freeze in YAML + smoke test

- Update [../usecases_synthetic/config/committees/<name>.yaml](../../usecases_synthetic/config/committees/) with the new roster. Preserve the `required_axes` enforcement block and make sure axis coverage is still satisfied (add/remove axes as the roster dictates).
- Each new member needs either an existing `module.class` pointer or a new adapter under `usecases_synthetic/lib/` (matching the `DittoMatcher` pattern). No core-PyDI changes.
- Run [../usecases_synthetic/tests/test_committee_configs.py](../../usecases_synthetic/tests/test_committee_configs.py) — must pass.
- Smoke test: instantiate every member on a 20-row fixture (use the `companies-small` slice) and confirm it produces a non-empty output without exception. No quality bar — this is shape-only.

Output: committee YAML updated + test green + one-paragraph `committee_review/<name>_rollup.md` linking back to the shortlist.

### Process requirement for every implementation row (C1.6, C2.4b, C3.4)

Applies to every remaining `[ ]` implementation row in the progress tracker. User-directed, 2026-04-22.

1. **Implement** the component (adapter, YAML wiring, test extensions).
2. **Rigorously test it for functionality** — beyond the shape-only smoke test above:
   - At least one **functional test per new member**, exercising the real code path on a realistic fixture, not just config validation. "Instantiates and returns a non-empty frame" is not sufficient on its own.
   - Known-good assertions where possible: deterministic members must pin a seed and assert exact outputs; NaN-tolerant members must have an explicit NaN-tolerance test; score-producing members must have a sanity assertion (e.g. strong positive pair scores above a floor, strong negative pair scores below a ceiling).
   - Edge cases: empty inputs, missing columns, unexpected shapes, and any axis the member claims to cover.
   - Run the full relevant test file (e.g. `test_committee_configs.py`, per-committee scoring tests) and capture the green output.
3. **Report back to the user with a final report** in the same turn as the green test output. Include:
   - Files changed (with line ranges / links to anchors),
   - Tests added or updated (file path + test name),
   - Exact commands run + pass/fail counts,
   - Any deviations from the plan and why,
   - Any follow-up items left open.
   - If the row was blocked partway (missing dep, failing test that exposes a deeper bug), ship the report framed as a blocker write-up instead of a completion report — do not skip reporting.
4. **Do not modify original PyDI code** (anything under [../PyDI/](../../PyDI/)). User-directed, 2026-04-22. New adapters, wrappers, prompts, vendored code, and committee-specific infrastructure land under [../usecases_synthetic/lib/](../../usecases_synthetic/lib/) or [../usecases_synthetic/third_party/](../../usecases_synthetic/third_party/), not under `PyDI/`. The existing `DittoMatcher`, `MagnetoSMMatcher`, `ComaSMMatcher`, `BM25Blocker`, `MagellanMatcher` placements are the precedent. **If a change to `PyDI/` is genuinely required** (e.g. a bug that blocks progress, a missing extension point, a protected attribute that must become public), stop, flag it to the user, and wait for explicit sign-off before editing. Do not silently extend, refactor, or "improve" PyDI code as part of a committee row — treat `PyDI/` as read-only infrastructure from the synthetic pipeline's perspective. This supersedes the C3.4 row's earlier inline note (*"add any adapters under `PyDI/fusion/conflict_resolution/` — promote to core since fusion is not synthetic-specific"*); that instruction has been retired from the C3.4 row, and the `robust_aggregators` module that had briefly shipped under `PyDI/fusion/conflict_resolution/` on 2026-04-22 was moved to `usecases_synthetic/lib/robust_aggregators.py` the same day to bring C3.4.1 into compliance. No grandfathered exceptions.

Why: downstream measurement depends on every committee member behaving correctly. A member that "loads without error" but silently returns wrong scores corrupts every downstream metric; the functional-test bar + proactive final report is how we catch that before S4b and S5. PyDI is shared infrastructure across several projects and use cases beyond the synthetic pipeline — unilateral edits there risk breaking callers the synthetic tracker doesn't see, and the scope of review / CI that change warrants is different from synthetic-local work.

## C1 — Schema Matching committee

> **Second user-directed addition (2026-04-21).** After C1.5 (Magneto), the user also directed adding **COMA 3.0 CE** (via the Valentine Python wrapper) as an 8th committee member, overriding the C1.3 rejection (score 8, below the 10-cutoff — rationale in [sm_shortlist.md §Exclusion rationale (COMA specifically)](../../knobs/committee_review/sm_shortlist.md#exclusion-rationale-coma-specifically--user-requested-evaluation)). Tracked as **C1.6** below. The C1.3 rationale (architectural redundancy, JRE dependency, pre-LLM performance ceiling) remains on record; inclusion is on historical-importance + hybrid-aggregation-reference-implementation grounds rather than rubric-score grounds.

> **Label-based removal (user-directed, 2026-04-22 — tracked as C1.7).** `label_jaccard` and `label_jaro_winkler` removed from `sm_committee.yaml`. Rationale: K8 (anonymised headers) collapses the label signal outright, and on non-anonymised headers `embedding_sbert` subsumes it (SBERT over the column name captures the same surface similarity + semantic generalisation). See [sm_shortlist.md §User Decision — 2026-04-22 (label removal)](../../knobs/committee_review/sm_shortlist.md#user-decision--2026-04-22-remove-label_jaccard-and-label_jaro_winkler).

> **Instance-tfidf removal (user-directed, 2026-04-22 — tracked as C1.8).** `instance_tfidf_cosine` also removed from `sm_committee.yaml`. Rationale: `embedding_sbert` encodes column name + sample values via SBERT, so cosine similarity over those dense embeddings subsumes TF-IDF-over-values as a value-distribution signal (keeping both double-counts the axis). `required_axes.signal_type` reduced from `[label, instance, duplicate, embedding]` (C1.3 target) to `[duplicate, embedding]` (after C1.7 + C1.8). See [sm_shortlist.md §User Decision — 2026-04-22 (instance-tfidf removal)](../../knobs/committee_review/sm_shortlist.md#user-decision--2026-04-22-remove-instance_tfidf_cosine).

**Current roster (3 wired after C1.7 + C1.8) in [sm_committee.yaml](../../usecases_synthetic/config/committees/sm_committee.yaml):** `duplicate_majority`, `embedding_sbert`, `llm_openai`; plus `magneto_slm_llm` (opt-in via `--with-llm`). Pending addition: `coma_hybrid` (C1.6, enabled by default once wired).

**Coverage gaps to investigate:**
- **Embedding-based label/column matching** — current label signal is pure string similarity; modern SM methods (SemTab, Magneto, Unicorn, SMAT) use contextual embeddings of column headers + values. Likely slot.
- **Instance-based beyond TF-IDF** — deep-learning columns-as-sets representations (DeepMatcher-SM, Valentine's Cupid/COMA variants).
- **Hybrid/ensemble reasoners** — papers like Magneto explicitly mix signals; we currently ensemble five heterogeneous members but don't have a "learned-to-combine" option.
- **Zero-shot LLM prompt matchers other than OpenAI** — diversity of LLM providers / prompt styles (table-question prompts vs chain-of-thought).

**Required axis coverage for the final roster (updated 2026-04-22 after C1.7 + C1.8):**
- `signal_type`: at least one of each of `duplicate`, `embedding`, with `llm` (opt-in) and `hybrid` (pending C1.6) on top. `label` and `instance` are no longer required — `label` collapses under K8, `instance`-via-TF-IDF is subsumed by `embedding_sbert`'s SBERT encoding of sample values.
- Deterministic fallback (currently `duplicate_majority` + `embedding_sbert`) must remain so `--with-llm=false` runs are reproducible.

**External search queries (step ii):**
1. `"schema matching" "large language model" 2024..2026`
2. `"column type annotation" benchmark 2023..2026`
3. `"Valentine" OR "Unicorn" OR "Magneto" schema matching`
4. `"semantic type detection" schema matching 2024`
5. `"holistic schema matching" survey 2023..2026`
6. `schema matching transformer pretrained 2024..2026`

Portfolio anchors to expand from: [valentine_schema_matching](../../literature-search-generation/valentine_schema_matching/), [magneto_schema_matching](../../literature-search-generation/magneto_schema_matching/), [xbenchmatch_schema_matching](../../literature-search-generation/xbenchmatch_schema_matching/).

**Deliverable:** 5-6 member SM committee with at least one SOTA post-2023 method in the roster. Expected addition: a Magneto- or Unicorn-style embedding+LLM hybrid (concrete choice deferred to the shortlist output).

## C2 — Entity Matching committee

> **User-directed.** Like C1.5, the EM committee finalisation will be user-directed: the user reviews the portfolio + external search + scored shortlist (C2.1–C2.3) and then explicitly picks which methods to wire into [em_committee.yaml](../../usecases_synthetic/config/committees/em_committee.yaml) (C2.4). The rubric in the "Shared methodology → Step (iii)" section is advisory, not dispositive — the user may override cutoffs (as they did for Magneto in C1.5).

> **Architectural decision (user-directed, 2026-04-21).** The EM committee is split into **two separate committees**: a **blocking committee** (rule-based + embedding blockers) and a **matching committee** (learned + LLM matchers). The two committees are configured independently and composed at pipeline-run time. C2.4 implements the split.
>
> **Matching committee — fixed roster (4 members, updated 2026-04-22):** `ditto_plm`, `llm_matcher` (prompts upgraded to MatchGPT-style templates — absorbs MatchGPT design without the no-LICENSE dependency), `magellan`, `comem`. Sudowoodo, Splink, HierGAT, standalone MatchGPT are **excluded**. **Unicorn** was in the 2026-04-21 freeze but was dropped on 2026-04-22: per-domain DeBERTa fine-tune + GPU requirement not worth a single matching slot that overlaps `ditto_plm`'s learned axis (rubric score 8, already below the 10-cutoff — see [em_shortlist.md row 11](../../knobs/committee_review/em_shortlist.md#scoring-matrix)).
>
> **Blocking committee — roster TBD.** The three rule members (`token_rule`, `embedding_rule`, `standard_rule`) move from the old combined committee to the new blocking committee; additions (e.g. SC-Block, Sudowoodo's FAISS encoder) are a follow-up decision. See [em_shortlist.md §User Decision](../../knobs/committee_review/em_shortlist.md).

**Current roster (5 members) in [em_committee.yaml](../../usecases_synthetic/config/committees/em_committee.yaml):** `token_rule`, `embedding_rule`, `standard_rule`, `ditto_plm`, `llm_matcher` (opt-in).

Ditto is already the SOTA-PLM slot (Phase A0 done). The question for C2 is whether the other 4 slots should stay rule-based-heavy or whether a second learned member (HierGAT, MCAN, AnyMatch, Sudowoodo, Jellyfish) is justified.

**Coverage gaps to investigate:**
- **Zero-shot / few-shot LLM matchers without fine-tuning** — AnyMatch, Jellyfish, LEMONADE, TailorMatch. Currently only an opt-in LLM slot exists with no retrieval augmentation.
- **Graph-based / attention-pooling matchers** — HierGAT, MCAN operate on attribute-level attention rather than serialized-pair text; distinct signal from Ditto's BERT-on-serialized-text approach.
- **Contrastive-learning / self-supervised EM** — Sudowoodo, BarlowMatch, contrastive pre-training. Could complement Ditto as a second learned member that doesn't require gold labels.
- **Knowledge-distilled small models** — DISTILLER, small-Ditto variants for CPU-only deployment. Lower priority (Ditto already runs on MPS).
- **Blocking diversity** — current blockers are `TokenBlocker`, `StandardBlocker`, `EmbeddingBlocker`. Consider FAISS/HNSW-accelerated embedding blocker (we already have `hnsw` extra in pyproject); LSH; sparse-dense hybrid (SparkER, JedAI).

**Required axis coverage for the final roster:**
- `blocking_type`: `lexical`, `embedding` (present), add `hybrid` if a dense-sparse blocker lands.
- `matching_type`: `rule`, `learned` (present), add `llm` (currently opt-in — evaluate promoting).
- `missing_value_tolerant`: at least one non-PLM option (currently only Ditto satisfies this — rule-based matchers fail on NaN). Candidate: a comparator that treats NaN as wildcard, or a second learned matcher with NaN tolerance.

**External search queries (step ii):**
1. `"entity matching" benchmark 2024..2026`
2. `"entity resolution" large language model 2024..2026`
3. `"Ditto" OR "HierGAT" OR "Sudowoodo" OR "Jellyfish" entity matching`
4. `"zero-shot entity matching" 2024..2026`
5. `"contrastive learning" entity resolution 2023..2026`
6. `"Jellyfish" OR "AnyMatch" OR "LEMONADE" OR "TailorMatch" matching`
7. `"blocking" entity matching transformer 2023..2026`
8. Mannheim WBSG repos: `https://github.com/wbsg-uni-mannheim` (TailorMatch, etc.)

Portfolio anchors to expand from: [ditto](../../literature-search-generation/ditto/), [anymatch_zero_shot_em](../../literature-search-generation/anymatch_zero_shot_em/), [lemonade_llm_guided_em](../../literature-search-generation/lemonade_llm_guided_em/), [jellyfish_llm_data_preprocessing](../../literature-search-generation/jellyfish_llm_data_preprocessing/), [finetuning_llm_em](../../literature-search-generation/finetuning_llm_em/), [mixer_latent_interpolation_er](../../literature-search-generation/mixer_latent_interpolation_er/), [distiller_knowledge_distill_er](../../literature-search-generation/distiller_knowledge_distill_er/), [comem_match_compare_select](../../literature-search-generation/comem_match_compare_select/).

**Deliverable:** 5-7 member EM committee with diverse blocking + matching signals. Expected addition: one contrastive/self-supervised learned matcher (Sudowoodo or similar) or a retrieval-augmented LLM matcher (LEMONADE-style) to complement Ditto's supervised PLM path.

## C3 — Data Fusion committee

> **User-directed.** Like C1.5 and C2, fusion-committee finalisation will be user-directed: C3.1–C3.3 produce the portfolio / external-search / scored shortlist outputs, and the user then explicitly picks which strategies to wire into [fusion_committee.yaml](../../usecases_synthetic/config/committees/fusion_committee.yaml) (C3.4). Given the thin existing portfolio + the fusion-specific hard-blockers flagged below, expect the user to adjudicate edge cases on LLM-cost / integration-cost trade-offs.

> **Fixed roster (user-directed, 2026-04-21) — 7 members:** `fusionquery`, `truthfinder`, `ltm`, `casefusion`, `accusim`, `llm_as_judge`, `robust_aggregators`. All four baselines (`truthfinder`, `ltm`, `casefusion`, plus `fusionquery` itself) ship in a single Apache-2.0 vendor operation from [JunHao-Zhu/FusionQuery](https://github.com/JunHao-Zhu/FusionQuery); `accusim` is paper-reimplemented from Dong et al. VLDB 2009; `llm_as_judge` and `robust_aggregators` are in-house. KDEm dropped on author-disowned + no-LICENSE; CRH / CATD dropped on redundancy after LTM + CASE added. All 5 TD methods are unsupervised (no labels, no training corpus, no pretrained checkpoints); CASE uses SGD as an optimizer but on a fully structural loss over the source-claim graph. Five distinct TD paradigms covered: iterative mutual reinforcement (TruthFinder, AccuSim), EM-style joint estimation (FusionQuery), Bayesian+Gibbs (LTM), unsupervised graph-embedding (CASE), LLM arbitration (llm_as_judge). Relaxed-licensing stance applies: reference code "in any form" accepted for this roster. See [fusion_shortlist.md §User Decision](../../knobs/committee_review/fusion_shortlist.md).

**Current roster per attribute in [fusion_committee.yaml](../../usecases_synthetic/config/committees/fusion_committee.yaml):** 3-4 strategies per attribute drawn from `voting`, `longest_string`, `most_complete`, `median`, `maximum`, `earliest`, `union`, `favour_sources`, `prefer_higher_trust`. All are cell-local or trust-weighted.

**Coverage gaps to investigate:** Fusion is the under-served committee — the literature portfolio currently has no dedicated fusion papers (search confirmed: grep over `literature-search-generation/` shows zero entries whose method class is "fusion" / "conflict resolution" / "truth discovery"). External search will carry most of the weight.

- **Truth-discovery / probabilistic fusion** — TruthFinder, LTM, Accu, latent-truth models. These score sources by accuracy and weight them jointly with the fused value — a learned analogue of `prefer_higher_trust`. SOTA fusion for multi-source.
- **LLM-driven conflict resolution** — recent papers on using LLMs as judges over conflicting cells (especially where semantic equivalence matters: "NYC" vs "New York" vs "New York City").
- **Entity-aware fusion** — current committee is cell-local + trust-weighted; entity-aware means using cross-cell consistency (e.g., `country=USA` should constrain `city` to US cities). Relevant for K10 signal.
- **Numeric fusion beyond median/max** — robust statistics (trimmed mean, Huber M-estimator), distribution-aware (if values come from skewed distributions).
- **Source-trust learning from gold** — semi-supervised trust learning rather than the manual trust_scores we ship today.

**Required axis coverage for the final roster:**
- `strategy_type`: `cell_local`, `trust_weighted` (present), add `truth_discovery` and/or `llm_adjudicated`.
- At least one data-driven strategy per attribute class (primary / secondary / key).
- Deterministic fallback per attribute must remain.

**External search queries (step ii) — carry most of the weight here:**
1. `"data fusion" "conflict resolution" survey 2020..2026`
2. `"truth discovery" data integration 2023..2026`
3. `"TruthFinder" OR "LTM" OR "Accu" OR "latent truth" data fusion`
4. `"large language model" data fusion OR conflict resolution 2024..2026`
5. `"multi-source data integration" trust 2023..2026`
6. `"holistic data fusion" OR "joint entity and value resolution" 2022..2026`
7. `Dong Srivastava data fusion` (anchor author — Xin Luna Dong's group)
8. `robust aggregation numeric conflict data integration`

Portfolio anchors: none directly; start from the EM surveys ([christophides_er_survey](../../literature-search-generation/christophides_er_survey/), [heterogeneity_em_survey](../../literature-search-generation/heterogeneity_em_survey/)) which sometimes touch fusion in a later chapter.

**Deliverable:** fusion_committee.yaml with at least one truth-discovery strategy added to the primary-class attributes (`name`, and potentially `industry` / `country` / `city` once lifted from key-class to include a truth-discovery option). Numeric attributes (`assets`, `revenue`) should gain a robust aggregator (trimmed mean or similar).

## Hard blockers (what might slip)

- **External literature search bandwidth.** Google Scholar rate limits + paywalled VLDB/SIGMOD PDFs mean step (ii) is wall-clock-dominated. Budget: ~30-60 min per committee. If a venue requires institutional access, log the paper title + venue in the external.md file and move on rather than blocking on the PDF.
- **New adapters.** Any shortlisted method that lacks a code release + Python API becomes an unbounded implementation task. Rule: if the paper has no code and the method description would take > 1 day to re-implement, score it 0 on "Integration cost" and drop it — we are picking a *working* committee, not a research survey.
- **Fusion methodology gap.** C3's portfolio is thin. If external search doesn't surface a well-maintained truth-discovery implementation, fall back to wiring one of the classical methods (TruthFinder or a simple weighted-majority voter with source-accuracy estimates) as a pure-Python adapter. Ship one additional fusion strategy even if it's modest; the current roster is entirely heuristic.
- **LLM cost.** Any shortlisted LLM-adjudicated fusion strategy runs against the shared LLM budget (`cross_cutting.md §LLM hygiene`). If C3.4 proposes an LLM member, include a cost estimate (pairs × prompts × model rate) in the committee YAML comment and flag to the user for approval before merging.
